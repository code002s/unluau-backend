# unluac-rs Working Conventions

Perform the minimum complete modification required to fulfill the current request, based on execution semantics, layer responsibilities, and verifiable results. This document maintains the project's working conventions; specific semantic contracts are kept in design documents and are not copied into skills or task logs.

## Execution Boundaries

- Implementation and verification proceed immediately upon a modification or fix request from the user; existing authorizations remain valid for subsequent steps. Low-risk ambiguities are handled by stating assumptions and proceeding; only critical missing information that would change the outcome requires clarification, and work not dependent on the answer should be completed first.
- Supplemental constraints or progress inquiries provided by the user during execution are integrated into the current task; unless the goal is explicitly cancelled or replaced, proceed after answering. When additional authorization is needed, prepare reviewable results first, then explain the specific action and the constraints it is based on.
- Before modifying, check workspace diffs and related call sites to preserve existing user changes. Deliver after completing the agreed scope and necessary verification; additional checks are triggered only by new failures or unresolved specific doubts, not by automatic full-repo audits.
- Skills serve the current request; explicit user requirements take precedence over skill suggestions. If a skill causes a pause, confirmation, or deviation from the task, point out the specific file and original sentence, distinguishing between explicit requirements and internal inferences.
- Use sub-agents as delegated by the user and the environment's permissions; parallelize only for independent sub-tasks that save time or improve quality, with clear file boundaries; the main agent is responsible for integration. Proofs and commit boundaries for the same pass must maintain unified responsibility.

## Task-Based Reading

- Before modifying pipeline implementations, read the [Maintenance Map](docs/design.md) and target layer documentation; trace cross-layer facts back to their producers. Documents, memory, and old reports are for navigation; current code and reproduction results are the basis for judgment.
- When reproducing decompilation errors or readability issues, use the [unluac-debug skill](.agents/skills/unluac-debug/SKILL.md); for command details, see the [Debug Manual](docs/debug.md). Ordinary documentation or build configuration changes do not load this diagnostic process.
- Use available `rust-skills` when writing, modifying, or reviewing Rust code; pure documentation tasks do not require it.
- The test protocol and verification scope are found in the [Test System](docs/design/11.test.md); read the [Lua Environment Description](lua/README.md) only when initializing or fixing the Lua toolchain.
- The `src` of each crate should only contain implementation; do not keep embedded Rust tests such as `#[test]`, `mod tests`, or `#[cfg(test)]`. When cleaning existing ones, migrate valuable cases to registered Lua samples; new tests should consistently use Lua samples.

## Audit and Verification

- Decompilation audits primarily follow the line of compiling, decompiling, regenerating source, and observing execution of supported Lua samples in `tests/`; prioritize current unit/regression failures. Construct the smallest sample that exposes the difference first, then locate the first loss of fact, erroneous acceptance, or proof rejection along the pipeline; issues in temporary real-world input should be refined into registered source regressions.
- Semantics, readability, and convergence are evidenced separately: samples must actually execute the tested path and observe results, evaluation counts, or order; readability regression is fixed using existing source/AST assertions for expected structure. Consistent execution results cannot replace structural assertions or general equivalence proofs, and structural assertions cannot replace execution verification.
- Check both the acceptance proof and rejection reasons for candidates, distinguishing between real semantic barriers, insufficient facts, and resource limits based on the Pass guard contract. Guards should not be loosened based on guesswork, nor should "not yet proven" be treated as permanently unoptimizable; rewrite only after completing facts in the corresponding layer.
- Preserve failing regressions and valid assertions that expose problems; do not hide issues by weakening assertions, skipping supported instances, or increasing convergence rounds. Fix conclusions are bound to the current sample, applicable dialect, and verification results; local success does not equal full matrix success.
- Continuously modify and centrally verify around the same root cause or complete theme; every check should be capable of discovering a specific failure that affects implementation or conclusions. Finalize themes by completing necessary checks according to the test system, rather than repeating full verification or fine-grained commits for every small change.

## Implementation Constraints

- Decompilation is based on preserving verifiable operations, control relationships, evaluation order, and debug binding facts from the original bytecode; it does not require the re-compiled binary layout to be identical. Structural recovery can eliminate mechanical wrappers introduced by itself, but cannot delete original explicit checks, calculations, or declarations based solely on path or value domain inference; internal expression organization must also obey this boundary and not add optimization switches that allow deviation from it. Unused and zero-length debug intervals do not imply a lack of source identity; provable initialization ownership must be preserved, and active intervals must not be forged.
- Facts are held by the earliest layer that can reliably prove them; subsequent layers consume existing queries/provenance. Check existing passes and shared helpers first; missing coverage of existing responsibilities should be fixed in the original owner.
- When multiple consumers need the same HIR control flow or abstract value facts, establish shared analysis and queries in the natural owner; audit whether previous layers lost facts, subsequent layers sufficiently consumed them, or if they were redundantly rebuilt. Shared analysis must clearly define its scope and invalidation conditions and cannot use expired snapshots after IR rewrites.
- Cross-layer identities, protocols, and lifetimes use explicit facts, clearly defining producers, consumers, and their valid boundaries; do not guess identities based on slot numbers, statement positions, or accidental shapes. When replacing redundant implementations, verify actual callers and original capabilities to maintain functionality and proof coverage.
- Do not use special-case handling in later layers, compatibility layers, or dual-track facts to mask confirmed upstream errors. When the root cause involves the core model or cross-pass ownership, complete the structural fix after defining boundaries, invariants, and verification scope, rather than using local masking because the change is large.
- The project is still in the testing phase; erroneous structures can be replaced directly. However, when involving public interfaces, storage formats, or real callers, the impact must still be verified; the testing phase is not a reason to ignore compatibility constraints.
- HIR/AST rewrites obey the [Pass guard contract](docs/design.md#pass-guard-合同). Semantic equivalence, atomic commits, and guards required by the target dialect are part of implementation correctness, not unnecessary defensive scaffolding.
- The core library must support WASM; new operations and dependencies must not break this distribution method.
- Avoid introducing implementations with O(n²) or higher complexity relative to input size, especially full-candidate scans or repeated analysis rebuilds. Optimizing existing hotspots requires a reachable call path and complexity analysis or measurement evidence; prioritize reusing indices, shared facts, and incremental invalidation mechanisms over guessing performance bottlenecks based on code shape.
- Decide on splitting based on responsibility and concern, not based on line count.

## Code Commenting

- Use short English `//!` in Rust file headers to describe the file's responsibility, input, and output; essential fact sources and layer boundaries for understanding the module may also be explained. Usually one to two paragraphs are sufficient; do not write candidate lists, guards, algorithm steps, or a history of fixes, nor repeat parent module introductions to satisfy a template.
- Place comments in their smallest applicable scope: invariants for types and fields near their definition, function contracts using `///`, and specific branches, evaluation order, or reasons for rejection/acceptance using nearby `//`. Local comments explain the "why" of the code that is not obvious; do not leave implementation details in file headers or move the entire header comment to the entry function.
- Use examples as needed for explanation; not every pass file header requires one. Examples helping to understand the whole module can stay in the overview; examples explaining a specific algorithm, boundary, or counter-example should be placed at the corresponding implementation. Public API usage, Errors/Panics/Safety contracts are kept as needed and not deleted to compress header comments.
- Maintain a single copy of the same reason at the point closest to the implementation; when modifying existing behavior, synchronize the rewrite or deletion of obsolete comments, rather than appending patch notes, case lists, audit conclusions, or migration history to the file header. Stable cross-layer contracts and navigation stay in the design documents; source code only retains explanations necessary for understanding the current implementation.
- Organize comments by content ownership, not by mechanical line limits; preserve useful invariants, fact invalidation conditions, and counter-examples. Classification and reasons required by the Pass guard contract remain close to the rejection or acceptance point and are not deleted for the sake of brevity. When only comments are changed, verify that the implementation remains unchanged and validate the format and affected documentation entries; do not report this as a run-time semantic verification.

## Documentation and Delivery

- Synchronize updates to public behavior, layer contracts, or maintenance entries with their corresponding documentation; local helper adjustments do not require rewriting unrelated design sections. `docs/design/` maintains layer responsibilities, sub-phase/pass navigation, fact production/consumption, and invalidation boundaries; specific candidates, guards, and algorithm branches are explained in the implementation, not copied item-by-item into design documents.
- Write verification results and unfinished scope in the current delivery; place temporary reports in `tmp/`. Do not add continuous audit logs or per-sample migration lists. Sample behavior and assertions stay in Lua; tags, purposes, and configurations follow the test protocol as the sole source of truth.
- When modifying decompile options, check default values in `src/decompile/options.rs`, as well as actual consumption points in `packages/unluac-cli/src/cli/args.rs`, `packages/unluac-cli/src/cli.rs`, `packages/unluac-js/src/index.ts`, `packages/unluac-wasm/src/lib.rs`, and `packages/unluac-web/`, and synchronize `README.md` / `README_cn.md`. Update according to exposure scope; do not force core-specific parameters onto all front-ends.
- Place temporary dumps and probes in `tmp/`, and do not rely on their persistence; source samples that need to be kept are placed in `tests/case_<type>/` and registered according to the test protocol.
- Use concise English to explain results, reasons, verification scope, and real limitations by default. Clearly distinguish between actual pass, not run, and existing failure; do not use historical pass counts to prove the current version.
- Use a one-line `type(scope): description` for commits, where type is one of `feat`, `fix`, `refactor`, `test`, `doc`, `chore`; this format convention itself does not require automatic commits.
